# TEKO STORE — تسجيل الطلبات ولوحة المالك

**الحالة الحالية: مجهز على GitHub فقط — لم يُفعّل على Supabase.**
استقبال ZIP وإرسال رابط واتساب مستمران. ميزة تسجيل الطلبات في قاعدة البيانات مغلقة عمدًا في order-cloud-config.js.

## 1. تجهيز قاعدة البيانات
افتح SQL Editor في Supabase، وانسخ محتوى:
supabase/migrations/20261121_teko_orders.sql

ينشئ جدول public.teko_orders مع RLS وبدون صلاحيات قراءة عامة، لحفظ بيانات العميل والهودي والمقاسات والكمية وحالة الطلب ومسار ZIP الخاص. لا يتم تخزين رابط ZIP الموقّع لانتهاء صلاحيته.

## 2. تحديث خدمة رفع الطلب
افتح:
supabase/functions/teko-order-link/index.ts

انشر النسخة الجديدة في Edge Functions > teko-order-link > Code.
تقبل هذه النسخة حقل order اختياريًا داخل finish بعد إثبات وصول ملف ZIP. ثم تحفظ بيانات الطلب وتعيد registered: true.
العملاء الحاليون الذين لا يرسلون الحقل order يظلون مدعومين، ولا تتغير عملية الرفع الحالية.
اترك Verify JWT = OFF مثل إعداد الوظيفة الموجودة.

## 3. إعداد حساب المالك
Supabase > Authentication > Users: أنشئ حساب المالك ببريد إلكتروني وكلمة مرور قوية.
انسخ UUID من User ID وأضفه في Edge Functions > Secrets باسم:
TEKO_OWNER_UID

تحقق الخدمة من هوية Supabase Auth وUser ID على الخادم، وليس اعتمادًا على البيانات المرسلة من المستخدم.

## 4. نشر خدمة الإدارة
انشر الملف:
supabase/functions/teko-admin-orders/index.ts

اسم الوظيفة: teko-admin-orders، واجعل Verify JWT = OFF، إذ يقوم الكود نفسه بالتحقق من JWT ومعرف المالك.
تتيح هذه الوظيفة عرض قائمة الطلبات، التفاصيل، تحديث الحالة، وإنشاء رابط تنزيل ZIP جديد لمدة 15 دقيقة.

## 5. إكمال إعداد واجهة المالك
افتح owner-config.js على GitHub، وأضف مفتاح Supabase Publishable العام في publicKey.
مكانه: Supabase > Project Settings > API Keys.
هذا المفتاح العام فقط يجوز تضمينه في الواجهة.

ممنوع إضافة أي مفتاح خاص مثل sb_secret_ أو service_role أو TEKO_HMAC_SECRET أو TEKO_CRON_SECRET أو مفاتيح Vault.

رابط لوحة المالك بعد تفعيلها:
https://oa1963507-commits.github.io/teko-store/owner.html

الجلسة تُخزن في ذاكرة الصفحة فقط؛ لا تُخزن كلمة المرور أو access token في localStorage.
لوحة المالك خاصة، وتظهر بيانات العميل فقط بعد تحقق الخادم من هوية المالك.

## 6. الاختبار والتفعيل
1. بعد تنفيذ SQL ونشر الوظائف، اختبر تسجيل الدخول إلى لوحة المالك.
2. اختبر تسجيل طلب جديد بملفات تجريبية.
3. تحقق من ظهور السجل داخل قاعدة البيانات ولوحة المالك، ومن إمكانية تغيير حالته.
4. تحقق من أن مستخدمًا غير مالك لا يستطيع رؤية الطلبات.
5. بعد نجاح الاختبارات، غيّر databaseOrdersEnabled إلى true في order-cloud-config.js وحدّث رقم Cache في index.html.

**لا تغير العلم الآن.** تفعيل الخاصية قبل نشر قاعدة البيانات والوظائف سيؤدي إلى تعذر تسجيل الطلب.

## ملاحظات
- وظيفة تنظيف الملفات teko-orders-cleanup تزيل ZIP بعد 7 أيام، لا سجل الطلب.
- الأسعار والعمليات المالية في الطلب بيانات مبدئية مقدمة من الواجهة، وليست إثبات دفع.
- راعِ سرية عناوين وأرقام العملاء، ولا تشارك لقطات شاشة بها بيانات فعلية.

## V28 — إحصائيات الطلبات والعملاء (مرحلة إضافية)

الكود المجهز في GitHub لا يغيّر وظيفة استقبال الطلبات، ولا يوسّع صلاحيات المتجر العام.

1. افتح Supabase > Edge Functions > teko-admin-orders > Code.
2. استبدل الكود المنشور بالكامل بأحدث نسخة من:
   supabase/functions/teko-admin-orders/index.ts
3. اضغط Deploy updates. أبقِ Verify JWT = OFF كما كان؛ الوظيفة نفسها تتحقق من جلسة Supabase Auth ومطابقة TEKO_OWNER_UID.
4. افتح owner-config.js في GitHub وغيّر reportsEnabled من false إلى true **بعد** نجاح النشر.
5. افتح owner.html وسجّل الدخول. تأكد من إحصائيات آخر 30 يومًا، ومختلف الفترات، وقسم العملاء والبحث والفلترة والواتساب وتصدير الصفحة الحالية CSV.
6. اختبر تغيير حالة طلب تجريبي ثم تحديث الإحصائيات. لا تستخدم طلب عميل حقيقي لأغراض الاختبار.

ملاحظات الأرقام:
- مبالغ الطلبات **عروض أسعار مبدئية** وليس إيرادًا أو مدفوعات مؤكدة؛ تستبعد الملغي.
- التقارير تعتمد على سجلات Supabase المركزية فقط منذ تفعيل تسجيل الطلبات، وليس رسائل واتساب القديمة غير المسجلة.
- في البداية البيانات قليلة؛ نقطة التقرير تقرأ حدًا أقصى 5000 طلب. عند تجاوز ذلك ستظهر عبارة واضحة بأن التحليل جزئي بدل الادعاء أنه دقيق لكامل المتجر.
- تنزيل CSV يشمل **الصفحة المعروضة فقط** وقد يحتوي على بيانات شخصية، فاحتفظ به في مكان خاص.
- تقرير العملاء يجمع الطلبات برقم الموبايل، ولا ينشئ حسابات للزوار.

كيفية الرجوع: غيّر reportsEnabled إلى false في owner-config.js؛ تظل إدارة الطلبات القديمة تعمل بدون تغيير، ولا تتأثر ميزة إرسال ZIP.

## V30 — مساحة التخزين ومسح ملفات ZIP يدويًا

**الحالة: الكود مجهز على GitHub، وقسم التخزين مخفي حتى إعادة نشر وظيفة الإدارة.**

### نشر الخدمة

1. افتح Supabase > Edge Functions > teko-admin-orders > Code.
2. استبدل الكود المنشور بمحتوى الملف المحدّث:
   supabase/functions/teko-admin-orders/index.ts
3. اضغط Deploy updates. اترك Verify JWT with legacy secret = OFF؛ الكود يتحقق من JWT ومعرف TEKO_OWNER_UID على الخادم قبل كل أمر.
4. في GitHub عدّل owner-config.js: غيّر storageEnabled من false إلى true بعد نشر الوظيفة، ثم حدّث owner-config.js?v في owner.html عند الحاجة.
5. افتح لوحة المالك owner.html، وسجّل الدخول، ثم افتح قسم التخزين السحابي.

### الاستخدام

- تعرض اللوحة حجم ملفات ZIP الخاصة بمتجر TEKO وعدد الملفات والنسبة التقديرية من سعة 1 GB المجانية.
- زر تحديث المساحة يعيد الجرد. قائمة الملفات تعرض تاريخ كل ZIP وحجمه وعمره، وتدعم الصفحات وتحديد ملف أو أكثر.
- **حذف المحدد**: اختر الملفات، اضغط حذف، ثم اكتب حرفيًا «حذف المحدد» واضغط تأكيد الحذف النهائي.
- **تفريغ جميع ملفات ZIP**: يتطلب كتابة «حذف الكل»، ويحذف حتى 500 ملف في عملية واحدة. إذا بقيت ملفات، كرر بعد تحديث المساحة.
- يُحذف الملف من Supabase Storage عبر واجهة التخزين المعتمدة وليس عبر SQL.
- الحذف نهائي؛ روابط ZIP المرتبطة برسائل واتساب تتوقف فورًا، حتى قبل مدة 7 أيام. سجل الطلب وحالته يظل موجودًا لكن تنزيل ZIP الخاص به سيفشل.
- الجدولة التلقائية لحذف الملفات بعد 7 أيام تبقى فعالة.

### حدود ودقة الإحصاءات

- لا تعرض اللوحة إجمالي مساحة مشروع Supabase أو استهلاك الفوترة: النسبة مقارنة بالسعة المرجعية 1 GB، وتخص bucket باسم teko-orders فقط.
- تعتمد البيانات على metadata.size المتاحة من Storage API. إن تعذّر قراءة حجم بعض الملفات أو تجاوز الجرد 5000 ملف، تظهر عبارة «غير مكتمل» ولا يُعرض المتبقي كرقم مؤكد.
- الاحتساب الرسمي لـStorage في Supabase يعتمد على متوسط GB-hours خلال دورة الفوترة؛ حذف الملفات قد لا يزيل أي قيود مرتبطة بالاستهلاك المتوسط فورًا.
- راجع Supabase > Usage للمقارنة بالمساحة المعتمدة لدى المنصة.

### احتياطات الأمان

- الإجراءات متاحة بعد تسجيل الدخول بمفتاح JWT والتحقق على الخادم من TEKO_OWNER_UID؛ لا مفاتيح Service Role أو أسرار في GitHub Pages.
- أي حذف يتطلب إقرارًا صريحًا، ويحصر الخادم المسح في ملفات orders/*.zip داخل bucket teko-orders فقط.
- انتبه إلى الملفات الخاصة بالطلبات الجديدة: تفريغ الكل يؤثر فيها أيضًا وقد يقطع وصول العميل للمطبوعات.
- الرجوع عن الواجهة: اجعل storageEnabled = false. لا يغيّر ذلك ملفات Storage أو وظيفة الحذف التلقائي.
