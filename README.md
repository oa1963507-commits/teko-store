## المرحلة V39 — زر تثبيت TEKO كتطبيق من قائمة الموبايل

- زر **«تثبيت TEKO كتطبيق»** داخل القائمة ذات الثلاث شرط في أعلى واجهة الموبايل.
- عند دعم المتصفح للـ `beforeinstallprompt`، الضغط يعرض تأكيد التثبيت الأصلي؛ لا يبدأ التثبيت من تلقاء نفسه.
- عند عدم دعم التثبيت المباشر، تظهر تعليمات مناسبة لأندرويد (Chrome) أو آيفون (Safari / إضافة إلى الشاشة الرئيسية).
- عند فتح الموقع في وضع التطبيق المستقل، يظهر أن TEKO مثبت بالفعل، ويُعطل زر التثبيت.
- إضافة `sw.js` بنطاق خاص بالموقع ومسار شبكة فقط، **دون حفظ بيانات العملاء أو صور التصميمات أو الملفات السحابية في التخزين المؤقت**.
- تحديث `mobile.css` و`mobile.js` و`index.html` دون المساس بمنطق الاستوديو والسلة والطلبات.
- تثبيت PWA ليس تنزيل APK ولا نشرًا في Google Play أو App Store؛ قد لا تعرض المتصفحات طلب التثبيت المباشر فورًا، لذلك يتوفر المسار اليدوي.
- اختبار تجريبي مطلوب على أجهزة Android وiOS بعد نشر GitHub Pages؛ وجود الملفات في المستودع لا يؤكد ظهور مطالبة التثبيت على جهاز بعينه.

## الوضع الحالي

- محرر الهودي بأربع زوايا، ورفع التصميمات الأصلية، والنصوص، وضبط مكان الطباعة والمقاسات.
- رفع ZIP الخاص لكل طلب إلى Supabase Storage، مع روابط تحميل موقعة لمدة 7 أيام وإرفاق الرابط في نص واتساب.
- حماية الرفع بـ Cloudflare Turnstile. عند تعذر الرفع يمكن تنزيل ZIP ومشاركته يدويًا.
- تم إعداد وظيفة وجدولة Supabase لحذف ملفات ZIP التي تتجاوز 7 أيام. راجع سجلات Cron وEdge Function عند متابعة التشغيل.
- حفظ مسودة التصميم محليًا في المتصفح (IndexedDB).
- **معرض التصميمات التجريبي مستقل تمامًا عن Supabase**: إضافة الصور إليه تستخدم localStorage داخل متصفح المالك فقط. لا تتغير مساحة ZIP بسبب إضافة تصميم للمعرض. هذه الإضافات لا تظهر تلقائيًا على أجهزة العملاء أو المتصفحات الأخرى؛ لتوفير معرض عام دائم يجب وضع الأصول في مستودع GitHub Pages ونشرها كملفات ثابتة.
- عند اختيار تصميم للطلب، تُضم نسخة منه إلى ملف ZIP الخاص بالطلب فقط؛ وحذف ملف ZIP لا يحذف تصميم المعرض الأصلي.

## المرحلة V33 — واجهة المتجر والسلة المستمرة

- واجهة Home منفصلة عن استوديو التصميم، بأسلوب Dark Premium (أسود/أحمر) وبصور منتجات موجودة بالفعل داخل المستودع، دون توليد أي صور.
- اختيارات الصفحة الرئيسية تنقل المستخدم لاستوديو التصميم بنفس صور الهودي والتحكم في الزوايا ومواقع الطباعة.
- سلة محلية دائمة على **نفس المتصفح والجهاز** بواسطة IndexedDB، تحفظ اللون والمقاس والكمية والصور الأصلية ومواضع الطباعة لكل تخصيص.
- يمكن تعديل كل تخصيص، حذف منتج، تغيير الكمية، وإتمام سلة تحتوي عدة تخصيصات في **طلب واحد**.
- عند إتمام السلة يُنشأ ZIP واحد يحتوي مجلدًا مستقلًا لكل هودي (أربع زوايا + الأصول الأصلية + المقاسات) ويرفع عبر تدفق Supabase الحالي المحمي بTurnstile؛ مع تسجيل الطلب كصف واحد يحمل تفاصيل جميع عناصر السلة في order_payload.
- تظهر عناصر السلة المتعددة في تفاصيل طلب لوحة المالك الخاصة. لا تحتاج الميزة إلى تغيير Schema قاعدة البيانات أو نشر Edge Function إضافي.
- الحد الأقصى للسلة: 6 تخصيصات، 100 قطعة بالمجموع، 32 عنصر طباعة و40MB للملف الواحد.
- عند تعذر التسجيل السحابي يمكن تنزيل ZIP يدويًا وإكمال واتساب؛ في تلك الحالة قد لا يظهر الطلب المركزي.
- السلة **لا تستخدم Supabase للتخزين المسبق**، ولن تظهر على جهاز آخر، وقد تختفي عند مسح بيانات الموقع أو استخدام التصفح الخاص.
- لا تُحذف السلة تلقائيًا عند فتح رسالة واتساب؛ لأن فتح واتساب لا يثبت إرسال الطلب.
- تظل وظيفة شراء هودي واحد من المحرر موجودة دون تغيير.

- قاعدة بيانات public.teko_orders مؤمنة عبر RLS ومخصصة للخدمات الخلفية فقط.
- كل طلب جديد يُسجّل بعد وصول ZIP إلى التخزين، مع ظهور بياناته في لوحة المالك.

- عند تعذر الرفع أو التسجيل توجد طريقة تنزيل ZIP يدويًا، وقد لا ينشأ سجل مركزي في تلك الحالة.

ملاحظة: تسجيل الطلب في قاعدة البيانات لا يعني أن العميل ضغط زر «إرسال» داخل واتساب، ولا يعني تأكيد الدفع.

## الأمان

- ملفات العملاء وبياناتهم لا تُرفع إلى GitHub ولا تُدرج في ملفات المشروع.
- التخزين الخاص محمي بـ Supabase signed URLs، بينما الوصول إلى الطلبات في لوحة المالك يتم بعد تحقق Supabase Auth ومعرف المالك.
- لا تضع service_role أو sb_secret_ أو الأسرار الأخرى في JavaScript علني.
- واجهة لوحة المالك التجريبية داخل المتجر الحالي ما زالت محلية وغير آمنة للطلبات المركزية؛ لوحة owner.html الجديدة مستقلة ومحمية بحساب المالك، بينما لوحة المتجر القديمة ما زالت تجريبية.
- أسعار العملاء في بيانات الطلب عروض تقديرية ولا تُعتبر مدفوعات مؤكدة.
